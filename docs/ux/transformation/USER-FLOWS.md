# User flows

| Role and entry | Decisions and actions | Results and recovery |
| --- | --- | --- |
| Admin signs in and opens Dashboard or Draft events | Create a draft in Cairo local time, save, appoint from the eligible Chief Leader group, wait for acceptance or record confirmed external acceptance, then publish. | Draft never appears in the Leader's view. Invalid fields keep entered values. Uncertain creation or appointment retries use existing idempotency. Publish confirmation explains notification and edit-lock consequences. A stale draft can be reopened separately without losing current input. |
| Admin opens an active event from Dashboard | Choose roster, roll sheet or More actions. Reschedule and closeout load the Admin event context and version. Cancel requires a reason. | Stale writes surface the failure and can reload the current context. Existing API lifecycle and authorization constraints decide which writes succeed. |
| Chief Leader receives an appointment | Follow the notification to the pending list. Check the event and choose Accept or Decline. | Review the current state after an uncertain response. Accepted appointments remain drafts until published by Admin. |
| Chief Leader opens an assigned event | Compare available candidates and direct-assignment candidates. Check factual history, select, or link a replacement to a prior cancellation. | Current roster updates after successful writes. Closed staffing windows disable changes. Lists can be searched and retried separately. Replacement linkage remains optional. |
| Chief Leader opens attendance | Mark outcomes one person at a time or mark all attended. Review unrecorded count and finalize. | Recorded outcomes remain visible. An Admin with correction rights can give a reason and correct a finalized outcome. Other unsaved entries remain in progress during a correction. |
| Leader signs in, or first registers | Registration requires Admin approval. Sign in, open Notifications, and read a published-event notice. | Failed authentication reports retry or connection errors. A pending registration explains the approval step. The workspace presents only the user's destinations. |
| Leader follows a published-event or assignment notice | Declare availability, view the active assignment, or submit a reason to cancel while the window is open. | Updated status is shown after server success. A native confirmation protects cancellation. The inbox links to the resources allowed for the role. |
| Leader opens profile | Review event dates, factual counts and cycle-specific history. Follow the current assignment and eligible feedback or incident paths. | Historical assignments and cancellations remain readable. Backend resource policy controls the specific feedback and incidents a user can view or submit. |

The implemented routes do not represent general event discovery, a separate application or final confirmation, or profile editing. Their absence is recorded in the [audit](UX-AUDIT.md).
