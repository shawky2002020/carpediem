# Carpediem Engineering Constitution

This constitution establishes the non-negotiable engineering principles, architectural boundaries, quality standards, and development governance for **Carpediem**.

---

## Core Engineering Principles

### I. Spec-Driven Development (SDD)
Development follows an artifact-based pipeline: `Constitution → Specification → Clarification → Plan → Tasks → Implementation → Convergence`. Implementation begins only after a feature specification and technical plan are reviewed and approved. Code must verifiably converge with its specification.

### II. Explicit & Testable Business Rules
All business logic, lifecycle rules, guard conditions, and domain invariants must be stated explicitly in specifications and verified by automated tests. Critical domain rules must never exist solely in client-side code (Angular); they must be enforced deterministically on the backend.

### III. Modular Monolith Architecture
Carpediem is architected as a Modular Monolith in ASP.NET Core. Modules represent logical and domain boundaries, not independent microservices or distributed systems. Cross-module communication occurs via clearly defined in-process contracts and abstractions. Distributed microservices are strictly prohibited without empirical evidence justifying architectural separation.

### IV. Domain & Module Boundaries
Each module encapsulates its domain entities, business logic, and data access. Direct cross-module coupling to internal entities is prohibited. Public module interfaces (contracts, commands, queries, events) are the sole mechanism for cross-boundary interaction.

### V. Server-Side Authorization & RBAC
All security, role-based access control (Admin, Chief Leader, Leader), and permission rules are strictly enforced server-side via ASP.NET Core policy-based authorization. Client-side route guards and visibility controls are strictly for user experience and provide zero security guarantees. Every privileged endpoint must have explicit automated authorization tests.

### VI. Relational Data Integrity
Data correctness is guarded at both the application layer and the persistence layer. Foreign keys, check constraints, unique constraints, nullability, and transactions must be explicitly modeled in the database schema. Data integrity must never rely solely on application-layer discipline.

### VII. SQL Server & T-SQL Engineering Depth
Microsoft SQL Server 2025 is the locked database engine. The engineering team must maintain direct command over T-SQL, execution plans, composite indexes, isolation levels, transactions, and concurrency handling. Database understanding must never be obscured behind Entity Framework Core. Engineers must be able to reason about and optimize the SQL generated by EF Core.

### VIII. API Contract Consistency & OpenAPI
REST APIs adhere to uniform conventions: standard HTTP verbs, appropriate status codes, RFC 7807 `ProblemDetails` for error reporting, and typed request/response DTOs. APIs must be fully described by OpenAPI specifications. Idempotency must be implemented where duplicate submissions risk data corruption.

### IX. Safe EF Core Migrations
All database schema evolution is managed through deterministic, reversible, and production-safe Entity Framework Core 10 migrations. Destructive schema changes (dropping columns/tables, data transformations) require a multi-phase migration strategy to ensure zero data loss and safe rollback paths.

### X. Auditability & History Preservation
Historical operational events (status changes, team selections, cancellations, replacements, attendance, and feedback) must preserve immutable audit records. Important operational records must not be destructively updated or silently overwritten; status transitions must track timestamps and actor identities.

### XI. Mobile-First UX (Non-Negotiable)
Carpediem is designed and implemented from the smallest mobile viewport first. The web interface must feel exceptional on mobile devices: comfortable touch targets (minimum 44x44px), thumb-zone reachability, short and focused forms, no horizontal scrolling in standard workflows, zero hover-only critical interactions, and graceful handling of network instability. Desktop layouts expand upon the mobile foundation.

### XII. WCAG 2.2 AA Accessibility
Accessibility is a core component of feature correctness. The application targets WCAG 2.2 Level AA compliance: semantic HTML elements, accessible form controls with explicit labels, logical keyboard navigation and focus management, sufficient contrast ratios, non-color-only status indicators, text-scaling resilience, and full support for `prefers-reduced-motion`.

### XIII. Performance & Layout Stability
Performance and stability are essential to correctness. Front-end code must prevent Cumulative Layout Shift (CLS), minimize blocking scripts, and optimize asset delivery. Core interactions must render with minimal latency. Heavy desktop-style data tables are prohibited on mobile viewports.

### XIV. Defense-in-Depth Security
Security practices must be embedded across all tiers:
- Authentication via ASP.NET Core Identity with secure HttpOnly cookie-based sessions as preferred default.
- Robust protection against OWASP Top 10 vulnerabilities (XSS, CSRF, injection, broken access control).
- Principle of least privilege applied to all user and system interactions.
- Strict protection of personal data and role-gated visibility for sensitive feedback.

### XV. Comprehensive Testing Pyramid
Quality verification requires layered testing:
- **Unit Tests**: Domain logic, invariants, state machine transitions, and validation guards.
- **Integration Tests**: ASP.NET Core API endpoints using `WebApplicationFactory` and real SQL Server instances via `Testcontainers`.
- **Contract Tests**: Request/response validation and HTTP status compliance.
- **End-to-End (E2E) Tests**: Critical user workflows (auth, selection, confirmation, attendance) tested in Playwright.
- **Performance Tests**: Realistic workload benchmarks using k6 based on actual project scale (~100–150 Leaders).

### XVI. Observability & Telemetry
Production operations must be observable: structured logging via Serilog, distributed tracing and metrics via OpenTelemetry, standardized health check endpoints (`/healthz`), and correlation/request ID propagation across every request.

### XVII. Simplicity & No Premature Infrastructure
Every architectural component, framework, or dependency must solve an immediate, demonstrable requirement. Do not introduce message brokers (Kafka, RabbitMQ), distributed caches (Redis), container orchestrators (Kubernetes), or microservices architectures for speculative scale. Default to standard in-process solutions (`BackgroundService`, `IMemoryCache`) until empirical bottlenecks justify expansion.

### XVIII. Definition of Ready (DoR)
A feature cannot enter implementation until its prerequisites are satisfied:
- Problem statement, actors, and preconditions defined.
- Functional business rules and validation constraints explicit.
- Server-side authorization rules documented.
- State transitions and invariants mapped.
- Edge cases and error paths identified.
- Acceptance criteria testable.
- Major open questions resolved.

### XIX. Immutability of Locked Specifications
Once a specification, story, or plan reaches `LOCKED` status, it cannot be silently modified by an implementation agent. If implementation uncovers an unforeseen blocker or requirement change, implementation must immediately pause, a formal clarification or change note must be reviewed, and the specification must be formally re-approved.

### XX. Architecture Decision Records (ADRs)
Significant architectural choices, technology adoptions, structural boundaries, and security patterns must be recorded in Architecture Decision Records using the MADR format under `docs/decisions/`. Code changes that alter system architecture require an associated approved ADR.

---

## Governance & Amendment Rules

1. **Constitutional Precedence**: This Constitution represents the highest engineering authority in the repository and supersedes informal discussions, scratch notes, or implementation suggestions.
2. **Review & Compliance**: All Pull Requests, design documents, and AI-assisted implementation tasks must verify compliance with this Constitution.
3. **Amendment Procedure**: Amendments require documented justification, stakeholder/architect approval, and an associated migration plan if existing code or architecture is affected.
